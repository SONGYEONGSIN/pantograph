# Pantograph — 문서 재현 하네스 (설계)

> **이름 확정: Pantograph** (2026-08-06, 사람 결정). 아래 `## 이름` 절의 후보 비교와 추천 근거는 결정 시점 기록으로 그대로 보존한다.
> 출처: repick-prompt 의 `/reprompt` 2층 산출물 (DNA v1.23, target coding).

**추천: Pantograph** (CLI `panto`)

세 이름이 각각 재현·축적·복제를 담지만, 이 시스템의 정체는 **"원본을 보고 그대로 따라 그리되, 그 따라 그리기를 기계가 검증한다"**이다. 팬터그래프는 그 구조를 그대로 은유한다 — 한쪽 팔이 원본을 훑고 다른 팔이 사본을 그리며, **두 팔이 물리적으로 연결돼 있어 어긋날 수 없다.** 이 시스템에서 그 연결부에 해당하는 것이 렌더-비교-보정 루프다. 이름이 아키텍처를 설명한다.

이름 충돌(상표·패키지 레지스트리·기존 프로젝트) 확인은 `[확인 필요]`.

## 이 시스템이 푸는 문제

기존 방식들은 저마다 다른 이유로 실패하지만, **공통 결함이 하나 있다 — 틀렸는지 아는 방법이 없다.**

| 방식 | 실패 양상 |
|---|---|
| 객체 모델 라이브러리 (python-docx·openpyxl 계열) | 문서를 라이브러리의 객체 모델로 읽어 다시 쓴다. 모델이 커버하지 못하는 XML 요소는 **읽고 쓰는 과정에서 소실되거나 기본값으로 대체**된다(추정 — 라이브러리·버전별 커버리지 차이는 검증 필요). 증상: "문단 한 줄 고쳤는데 표 테두리와 머리글이 달라졌다" |
| LLM이 OOXML을 직접 생성 | OOXML은 스타일 상속·번호매기기·관계(rels)가 **파일 간 참조로 얽혀** 있다. 토큰으로 뱉은 XML은 참조가 어긋나 열리지 않거나, 열려도 서식이 무너진다 |
| 상용 변환 API | 블랙박스다. 결과가 다를 때 **무엇이 왜 달라졌는지 알 수 없고**, 에이전트가 손댈 표면이 없다 |

세 방식 모두 생성 후 **사람이 열어보기 전까지 재현 실패가 드러나지 않는다.** 에이전트에게 문서 제어권을 준다면서 "잘 됐는지"를 사람 눈에 의존하는 것이 근본 결함이다.

Pantograph의 주장은 하나다: **재현은 생성 문제가 아니라 측정 문제다.** 측정할 수 있으면 고칠 수 있고, 고친 것을 쌓으면 능력이 축적된다.

## 핵심 — 시각 재현을 어떻게 달성하는가

### 재현 파이프라인

```
입력(시안 PNG · PDF · 참조 docx)
  ↓ ① 구조 추출      블록·표·이미지·텍스트런의 경계와 속성
  ↓ ② IR 구성        포맷 독립 중간표현
  ↓ ③ 포맷 바인딩    IR → OOXML 조작 명령(배치 패치)
  ↓ ④ 산출           docx / xlsx / pptx
  ↓ ⑤ 렌더           헤드리스 → PNG
  ↓ ⑥ 비교           목표와 산출의 차이를 경로 단위로
  ↓ ⑦ 보정 명령 ─────┘ ③으로 되돌아감 (상한 있음)
```

**각 단계에서 무엇이 손실되는가** — 이걸 알아야 어디를 보정할지 정할 수 있다.

| 단계 | 손실 |
|---|---|
| ① 구조 추출 | **폰트 식별**. 렌더된 픽셀에서 폰트명을 역추론할 수 없다(추정: 폰트 지문 방식이 있으나 신뢰도 미검증). 자간·행간의 미세값, 색공간 변환 |
| ② IR 구성 | 포맷 고유 기능이 IR에 표현되지 않으면 소실 — 엑셀 수식, PPT 애니메이션, 워드 필드 코드 |
| ③ 포맷 바인딩 | IR 개념이 대상 포맷에 없으면 근사된다. 예: 자유 배치 그리드 → 워드 표 |
| ⑤ 렌더 | **렌더러와 실제 오피스 앱의 차이.** 이것이 가장 위험하다 — 우리 렌더러에서 통과해도 MS Word에서 다를 수 있다. 아래 미해결 위험 1번 |

### 차이를 무엇으로 재는가

**전체 페이지 픽셀 diff는 쓰지 않는다.** 1px 밀림이 페이지 전체를 빨갛게 만들고, 무엇보다 **어디를 고쳐야 하는지 알려주지 않는다.** 보정 루프의 입력이 되려면 지표가 경로를 가리켜야 한다.

IR의 블록 단위로 잰다.

| 측정 | 방법 | 가중치 |
|---|---|---|
| 텍스트 내용 | 정확 일치 | **최상** — 내용이 틀리면 문서가 틀린 것이다 |
| 구조·순서 | 블록 트리 비교 | 상 |
| 위치·크기 | 바운딩 박스 IoU | 중 |
| 스타일 속성 | 폰트·크기·굵기·색 값 비교 | 중 |
| 블록 내부 픽셀 | SSIM 등 유사도 | **하 — 관찰만** |

가중치를 이렇게 둔 이유: **사람은 1px를 못 알아채지만 빠진 문장은 알아챈다.** 픽셀 유사도를 게이트로 쓰면 사람이 무관심한 차이 때문에 루프가 헛돈다.

**합격 임계는 지금 정할 수 없다** — 벤치마크 문서 세트가 없기 때문이다 `[확인 필요]`. 초기 제안(제안이며 실측으로 교체되어야 함): *텍스트 100% 일치 + 블록 IoU ≥ 0.95 + 순서 일치*를 게이트로 두고 픽셀 유사도는 기록만 한다.

### 보정 루프

diff는 **경로 · 속성 · 기대값 · 실제값** 네 쌍으로 나온다.

```
word/body/tbl[1]/tr[3]/tc[2]/p[1]/r[1]  fontSize  expected=11  actual=10.5
word/body/p[7]                          align     expected=center  actual=left
```

에이전트는 이 경로에 대해 배치 패치를 만들고, 시스템이 재산출·재렌더·재비교한다.

- **개선되지 않으면 되돌리고 기록한다.** 되돌림 없이 계속 쌓으면 문서가 더 망가진다.
- **반복 상한**(제안: 3회). 넘으면 실패로 확정하고 그 사례를 볼트로 보낸다 — 수렴 실패가 곧 학습 재료다.
- **패치 생성은 시스템이 아니라 에이전트가 한다.** 자동 보정 규칙을 시스템에 넣으면 그 규칙이 굳어 학습 루프의 대상이 사라진다. 시스템은 **차이를 정확히 말해주는 것까지**가 역할이다.

### 대안 비교와 기각 사유

| 대안 | 왜 부족한가 |
|---|---|
| **템플릿 채우기만** (`{{key}}` 치환) | 레이아웃이 템플릿에 고정된다. 시안을 보고 만드는 게 아니라 **미리 만든 틀에 값만 넣는 것**이라, 새 시안이 올 때마다 사람이 템플릿을 만들어야 한다. 재현이 아니라 양산이다 |
| **LLM이 OOXML 직접 생성** | 위 문제 절 참조. 더 근본적으로, **틀렸을 때 어디가 틀렸는지 모른다** — 생성물 전체가 하나의 덩어리라 보정 지점을 지목할 수 없다 |
| **상용 변환 API에 위임** | 블랙박스. 실패 원인을 알 수 없어 보정 루프를 만들 수 없고, 학습할 재료도 남지 않는다. 정확도가 벤더 로드맵에 묶인다 |

세 대안의 공통 결함이 곧 이 설계의 존재 이유다 — **측정 가능한 차이와 그 차이를 가리키는 경로.**

## 조작 표면 계약

### 경로 문법

포맷별 루트 + 요소 인덱스/이름으로 주소를 만든다. 에이전트가 쓸 인터페이스는 **애매하면 오용되므로** 예시로 못 박는다.

```
word/body/p[12]/r[2]                     12번째 문단의 2번째 텍스트 런
word/body/tbl[1]/tr[3]/tc[2]/p[1]        1번 표 3행 2열의 첫 문단
xlsx/sheet[Sales]/A1:D20                 시트명 + 범위 (A1 표기 그대로)
xlsx/sheet[Sales]/A1/style               셀의 스타일 하위 노드
pptx/slide[3]/shape[title]/text          3번 슬라이드 title 플레이스홀더
pptx/slide[3]/shape[@name='로고']        이름으로 도형 지정
```

인덱스는 1-base(문서 편집자의 직관), 이름 지정은 `[name]`·`[@attr='v']`.

### 왕복 덤프 스키마 골격

```json
{
  "doc": { "format": "docx", "hash": "sha256:…", "dumpedAt": "…" },
  "nodes": [
    {
      "path": "word/body/p[1]",
      "type": "paragraph",
      "props": { "style": "Heading1", "align": "left" },
      "children": [
        { "path": "word/body/p[1]/r[1]", "type": "run", "text": "제목",
          "props": { "bold": true, "size": 16 } }
      ],
      "raw": "<w:p>…</w:p>"
    }
  ]
}
```

**`raw` 필드가 왕복 무손실의 열쇠다.** 스키마가 모르는 속성·요소는 원문 그대로 보존되고, 패치가 건드리지 않은 노드는 `raw`로 되돌려 쓴다. 객체 모델 방식이 소실을 일으키는 지점을 여기서 막는다. 시각 재현이 목표라도 **왕복 무손실은 그 전제**다 — 고칠 때마다 다른 데가 망가지면 보정 루프가 수렴하지 못한다.

### 배치 원자성

- 패치는 **트랜잭션**이다. 전부 적용되거나 전부 롤백된다.
- 경로가 하나라도 해석되지 않으면 **아무것도 적용하지 않고** 실패 목록을 반환한다. 부분 적용은 에이전트가 문서 상태를 잃는 최악의 실패다.
- **낙관적 잠금**: 덤프가 준 `hash`를 패치에 실어 보낸다. 그 사이 문서가 바뀌었으면 거부한다.

## 렌더링 엔진 선택

**"단일 바이너리"와 "렌더링 충실도"는 정면으로 충돌한다.** 둘 다 가질 수 없다는 것을 인정하고 2단으로 나눈다.

| 후보 | 장 | 단 |
|---|---|---|
| LibreOffice headless | 오픈소스 중 오피스 포맷 렌더 충실도 최상(추정) | 수백 MB·설치 필요 — 단일 바이너리 제약과 충돌 |
| 자체 렌더러 | 완전 제어·작은 바이너리 | OOXML 렌더링을 처음부터 구현하는 비용이 비현실적(추정: 사람-년 단위) |
| OOXML → HTML → 브라우저 엔진 | 이미지 목록의 "헤드리스 HTML/PNG"와 일치, 미리보기와 같은 경로 재사용 | **변환 충실도가 곧 렌더 충실도의 상한**이 된다 |

**선택**: 기본은 **내장 HTML 렌더**(빠른 루프용), 옵션으로 **LibreOffice가 설치돼 있으면 교차 검증**(정밀 판정용).

- 내장 렌더러는 보정 루프를 초당 수 회 돌리기 위한 것이다. 여기서 잡히는 차이가 대부분이다.
- LibreOffice는 최종 판정과 회귀 픽스처 채점에만 쓴다. 없으면 **없다고 보고하고 내장 렌더러 점수만 기록한다** — 조용히 통과시키지 않는다.
- 미리보기·CI·보정 루프가 모두 같은 렌더 경로를 쓰므로 "미리보기에선 맞았는데 CI에선 달랐다"가 생기지 않는다.

## 구현 언어와 배포 형태

제약에서 도출한다: *단일 바이너리* + *크로스 플랫폼* + *어떤 언어에서든 호출* + *헤드리스 CI*.

"어떤 언어에서든 호출"은 언어별 SDK를 만들라는 뜻이 아니라 **stdio로 JSON을 주고받는 CLI면 충분하다**는 뜻이다. 이것이 언어 선택의 자유도를 높인다.

| 후보 | 판단 |
|---|---|
| **Go** | 크로스 컴파일이 표준 기능이고 단일 정적 바이너리가 기본값이다. OOXML은 결국 zip + XML이라 표준 라이브러리로 충분하다 |
| Rust | 성능·메모리 안전 우위. 다만 OOXML 처리에서 그 우위가 결정적이지 않고, 크로스 컴파일 준비가 Go보다 번거롭다(추정) |
| Node/Python | 런타임 의존 — "설치 불필요 단일 바이너리" 제약과 정면 충돌. 번들러로 우회 가능하나 바이너리 크기·기동 시간에서 손해 |

**선택: Go.** 이 제품의 명시 제약이 성능이 아니라 **배포 단순성**이기 때문이다. 병목이 렌더링이라면 그건 언어가 아니라 렌더러 선택의 문제다.

## llm-wiki 진화 루프

### 볼트 구조

```
vault/
  00-principles/recipes.md        조작 레시피 DNA (버전 관리)
  10-references/                  외부 씨앗 — 스펙 발췌, 알려진 함정
  20-rounds/<date>-<slug>/        재현 시도 1건
      TARGET.md                   목표 문서와 무엇을 재현하려 했나
      attempts/                   시도별 패치·렌더·diff
      DECISION.md                 무엇이 통했나 / 왜
  30-ledger/fidelity.jsonl        시도별 점수 (append-only)
  40-fixtures/                    회귀 픽스처 — 승격된 실패 사례
```

### 승격 조건 (실패 → 회귀 픽스처)

- 재현 점수가 게이트에 미달했고, **원인이 레시피로 일반화 가능**할 때만 승격한다.
- **재현 가능해야 한다.** 1회성 입력 오류·환경 문제는 승격하지 않는다 — 픽스처는 매 라운드 재실행되므로 불안정한 것이 들어오면 신호가 노이즈에 묻힌다.

### 개정 판정 (레시피 개정)

- 같은 실패 부류가 **2회 이상 독립 발생**해야 레시피 후보가 된다. 1회는 우연과 구분되지 않는다.
- 판정은 4갈래: **신규 / 강화 / 충돌 / 애매.** 충돌·애매면 레시피를 고치지 않고 **질문을 남긴다** — 임의로 덮어쓰면 근거 없이 원칙이 흔들린다.

### 반증 장치

**이것이 없으면 학습 루프가 아니라 자기 확신 축적기다.**

1. 레시피를 고칠 때 **예측 델타**를 함께 적는다 — "이 개정으로 표 스타일 실패 부류의 점수가 X→Y로 오른다".
2. 다음 라운드가 **회귀 픽스처 전체를 재실행**해 실제 델타를 측정하고 ledger에 기록한다.
3. **예측이 빗나가면 개정을 되돌린다.** 레시피는 누적만 하는 목록이 아니라 반증되면 빠지는 목록이다.
4. 메타 지표: **픽스처가 늘어도 평균 점수가 오르지 않으면** 루프가 학습하지 않고 있다는 뜻이다. 그 정체 자체를 관찰 대상으로 둔다.

## 범위 밖

- **한글(HWP)·구글 문서·클라우드 협업** — 포맷 계열이 달라 별도 바인딩이 필요하다
- **PDF 편집** — PDF는 입력(참조)과 출력(렌더)으로만 다루고 편집 대상이 아니다
- **인증·과금·SaaS 대시보드·플러그인 마켓** — 이 설계는 재현 엔진과 진화 루프만 다룬다

## 미해결 위험

1. **렌더러는 실제 오피스 앱이 아니다.** 내장 렌더러와 LibreOffice 모두 MS Word의 실제 렌더링과 일치한다는 보장이 없다. **설계로 닫히지 않는 위험**이다. 완화: 2단 렌더로 좁히고, 실제 앱 스팟체크는 사람이 주기적으로. 이 격차 자체를 ledger에 기록해 추세를 본다.
2. **폰트가 정확도의 상한을 만든다.** 시안의 폰트를 픽셀에서 역추론할 수 없고, 대상 시스템에 폰트가 없으면 대체되어 레이아웃이 통째로 바뀐다. 폰트 가용성을 입력 조건으로 명시받아야 한다.
3. **합격 임계를 아직 정할 수 없다** — 벤치마크 문서 세트가 없다 `[확인 필요]`. 세트를 먼저 만들고 임계는 그 분포에서 도출해야 한다.
4. **형식 간 템플릿 병합의 의미가 불명확하다.** docx 템플릿에 xlsx 데이터를 넣는 것은 명확하지만 pptx→xlsx 방향은 무엇을 뜻하는가. 정의 없이 구현하면 아무도 안 쓰는 기능이 된다 `[확인 필요]`.
5. **보정 루프가 수렴하지 않을 수 있다.** 상한 3회(제안)를 넘으면 실패로 확정하고 볼트로 보낸다 — 수렴 실패율 자체가 시스템 성숙도의 지표다.

## 자기검증

구현할 엔지니어의 관점에서 "이대로는 못 만들겠다" 싶은 지점 3개를 찾아 본문에 반영했다.

1. **"IR을 어떻게 정의하는지가 없었다."** 포맷 독립으로 만들면 포맷 고유 기능을 잃고, 포맷 밀착으로 만들면 3포맷이 공유하지 못한다. → 본문에 **공통 코어 + 포맷별 확장**으로 나누고 확장은 `raw` 보존으로 처리한다고 명시했다.
2. **"diff에서 패치를 누가 만드는지 모호했다."** 시스템이 자동 보정하면 그 규칙이 굳어 학습 루프의 대상이 사라진다. → **시스템은 차이를 경로로 가리키는 것까지, 패치 생성은 에이전트**로 역할을 갈랐다.
3. **"첫 버전 범위가 너무 컸다."** 3포맷 + PDF + 렌더 + 진화 루프를 한 번에 만들 수 없다. → 명시적으로 **docx 하나로 수직 슬라이스**(덤프 → 패치 → 렌더 → 비교 → 루프)를 먼저 완성한 뒤 포맷을 넓힌다. 이 순서를 지키지 않으면 어느 층도 끝나지 않는다.
