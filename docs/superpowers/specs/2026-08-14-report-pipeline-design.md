# 보고서 파이프라인 — HTML 이 원본이고 나머지는 파생이다

**날짜**: 2026-08-14
**상태**: 승인됨
**선행**: [명시적 삭제](2026-08-12-explicit-delete-design.md) (PR #8)
**성격**: **이 슬라이스의 산출물은 대부분 문서와 얇은 스크립트다. Go 코드가 아니다** (§2)

---

## §1 무엇을 만드나

문서 생성 시스템의 첫 관통 경로. 보고서 한 종을 **내용 → 문서형 HTML → (덱형 HTML · PDF · 이미지)** 로 끝까지 흘린다.

```
요청 + 자료
    ↓   보고서 규격 (대상별 골격)
문서형 HTML   ← 원본 · 상세 · 사람이 읽고 고친다
    ↓ 압축 규칙              ↓ 인쇄 CSS
덱형 HTML                PDF · 이미지
```

폭이 아니라 깊이를 먼저 가는 이유: 이 세션에서 실물을 안 보고 세운 가정이 **세 번** 틀렸다. 형식 10종의 규격을 먼저 쓰면 그 오류가 열 배로 복제된다. 하나를 끝까지 통과시켜 구멍 목록을 확보한 뒤 복제한다.

## §2 이건 pantograph 가 아니다

이 파이프라인에서 pantograph(Go)가 하는 일이 **없다.**

| 단계 | 무엇이 하나 |
|---|---|
| 문서형 HTML 생성 | LLM 이 규격을 보고 쓴다 |
| 압축(문서형→덱형) | LLM 의 판단 |
| PDF · 이미지 | 헤드리스 크롬 호출 (스크립트 몇 줄) |
| HTML → PPTX · Word | **여기서 pantograph 가 등장한다 — 이번 범위 밖** |

이걸 인정하지 않으면 쓸 데 없는 Go 코드를 만들게 된다. 이번 슬라이스의 산출물은 **규격 문서 2개 + CSS 1개 + 스크립트 1개**다.

### 2.1 산출물을 어디 두나

디자인 시스템은 사용자 조직의 자산이고 이 저장소는 **공개**다. 둘을 섞지 않는다.

| 산출물 | 위치 | 이유 |
|---|---|---|
| 문서 시스템 스펙 (§3) | **저장소 밖** | 조직 자산 — 토큰 값·골격이 그 조직의 것 |
| 보고서 규격 (§4) | **저장소 밖** | 같은 이유 |
| 인쇄 CSS (§6) | 저장소 밖 | 디자인 시스템의 일부 |
| 변환 스크립트 (§6) | 저장소 | 범용 — 어떤 HTML 에도 쓰인다 |
| 이 설계 문서 | 저장소 | 아키텍처와 결정 이력. 조직 내용을 담지 않는다 |

이 문서는 계약의 **모양**만 적고 값은 적지 않는다.

## §3 문서 시스템 스펙 — 실물에서 도출한다

덱 시스템에는 이미 손으로 쓴 스펙이 있고 **실물과 22/22 일치**한다(색 토큰 10, 타입 스케일 12 실측). 문서 시스템에는 스펙이 **없다**.

지어내지 않는다. 실물 CSS 에서 뽑고, 뽑은 값을 실물과 대조해 검증한다 — 덱에서 일치를 확인한 것과 같은 방법이다.

담을 것:

- **변수** — 잉크·본문·보조·강조·강조배경·선·경고·경고배경·지면·바탕 (10종). 다크모드 대응값 포함
- **골격** — 문서 루트 아래 절 구조
- **장치** — 문서 종류 라벨 / 메타 정의목록 / 요약 문단 / 리드 / 노트 / 칩 / 표 / 절 번호
- **페이지 껍데기** — 아래가 이번 세션이 발견한 핵심 누락이다

### 3.1 페이지 껍데기 — 실측으로 드러난 누락

덱 스펙의 골격은 슬라이드 요소부터 시작한다. 그래서 그것만 보고 만든 덱이 **화면에 제대로 나오지 않았다.** 빠진 것 셋:

| 빠진 것 | 왜 치명적인가 |
|---|---|
| 무대(stage) 래퍼 | 슬라이드가 절대 위치라 래퍼 없이는 비율 상자가 성립하지 않는다 |
| 폰트 로딩 | 스펙은 폰트 **이름**만 적었다. 실제로는 외부 링크 3줄이 필요하다 |
| 렌더링 모드가 둘 | CSS 에 슬라이드 규칙이 두 벌(발표 모드 / 스크롤 모드). 스펙은 어느 쪽도 언급하지 않는다 |

**문서 시스템 스펙은 껍데기부터 적는다.** 골격만 있고 껍데기가 없는 규격은 "규칙은 다 지켰는데 안 보이는" 산출물을 만든다.

## §4 보고서 규격 — 여섯 필드

형식 하나를 여섯 필드로 정의한다. 이렇게 하면 나머지 형식 추가가 싸진다.

| 필드 | 무엇 |
|---|---|
| **대상** | 누가 읽나 + 수준 |
| **결정** | 이 문서가 가능하게 해야 하는 **행동 하나** |
| **골격** | 필수 절과 순서 |
| **분량** | 지면 수 |
| **증거 기준** | 무엇을 근거로 인정하나 |
| **금지** | 하지 말 것 |

뒤의 둘이 품질을 만든다. 덱 스펙 §7(작성 규칙)이 이미 덱용으로 이걸 갖고 있다 — 형식마다 갖게 하는 것이다.

**대상은 형식을 고르지 않는다. 같은 형식 안에서 골격을 바꾼다.**

| | 경영진 | 실무자 |
|---|---|---|
| 결정 | 승인 · 자원 배분 | 재현 · 인수인계 |
| 골격 | 결론 → 수치 → 리스크 → 요청 | 배경 → 과정 → 결과 → 재현 절차 → 한계 |
| 분량 | 1지면, 근거는 부록 | 제한 없음 |
| 증거 | 수치 + 출처 | 재현 가능한 절차 |
| 금지 | 과정 서술, 미해결 논의 | 결론만 쓰고 근거 생략 |

## §5 압축 규칙 — 버린 것을 신고한다

문서형 → 덱형은 **비가역**이다. 정보가 버려진다.

이 저장소가 `tmpl` 에서 내린 결론을 그대로 적용한다: **도구가 자기가 못 담은 것을 스스로 말한다.** `tmpl` 의 `unrepresented` 와 같은 역할을 덱형 산출물이 가진다.

압축 결과는 무엇이 빠졌는지 함께 낸다:

```
문서형 §3 "한계" 4항목  →  덱에 실리지 않음
문서형 표 12행          →  덱은 상위 5행 + "외 7건"
```

**압축이 조용하면 발표자는 자기가 무엇을 안 말하는지 모른다.** 이 저장소가 반복해서 처벌해 온 실패(도구가 성공이라 말하며 내용을 잃는 것)의 발표자료판이다.

압축 규칙 자체:

1. **결정과 수치는 버리지 않는다** — 보고서의 `결정` 필드가 요구하는 행동에 필요한 것
2. **한계·미해결은 버리지 않는다** — 버리면 덱이 실제보다 확신에 차 보인다
3. **과정 서술은 버릴 수 있다** — 다만 버렸다고 적는다
4. **표는 자르되 자른 사실과 건수를 남긴다**

## §6 변환 — 렌더링과 번역은 다르다

| | 성격 | 이번 범위 |
|---|---|---|
| HTML → PDF | **렌더링** — 보이는 대로 굳힌다 | 포함 |
| HTML → 이미지 | 렌더링 | 포함 |
| HTML → PPTX | **번역** — 다른 배치 모델로 옮긴다 | 범위 밖 |
| HTML → Word | 번역 | 범위 밖 |

번역이 어려운 이유는 도구가 아니라 **모델이 다르기 때문**이다. 이 디자인 시스템은 뷰포트 비례 단위 + flex + 절대 위치인데, 워드프로세서는 흐름 모델이라 대응물이 없다. 화면 비례 여백을 흐름 모델로 옮기면 그건 이미 다른 문서다.

### 6.1 인쇄 CSS — 실측된 결함

현재 덱 CSS 에는 인쇄 규칙이 **하나도 없다**:

```
슬라이드 6장  →  PDF 4페이지
@page: 없음 / break-after: 없음 / @media print: 없음
```

브라우저가 임의로 잘랐다. 필요한 것:

- 덱형: 1슬라이드 = 1페이지, 가로
- 문서형: 지면 규격, 절이 페이지 경계에서 갈리지 않게

### 6.2 스크립트

헤드리스 브라우저를 불러 PDF·이미지를 뽑는다. 이 저장소에 두는 유일한 코드다. 범용이므로 어떤 HTML 에도 쓰인다.

**측정된 전제**: 헤드리스 브라우저는 이 장비에 있다. 문서 변환 엔진(LibreOffice 계열)은 **없다** — 번역 변환을 외부 엔진에 맡길 생각이었다면 그 경로는 지금 막혀 있다.

## §7 검증

이 슬라이스는 Go 코드가 거의 없으므로 단위 시험이 아니라 **대조**로 검증한다.

| | 무엇을 확인하나 |
|---|---|
| **V1 스펙 정합** | 스펙에 적은 값이 실물 CSS 와 일치한다. 덱에서 22/22 로 확인한 것과 같은 방법 |
| **V2 껍데기 완결성** | 스펙만 보고 만든 산출물이 실제로 화면에 나온다. 오늘 이게 실패했다 |
| **V3 페이지 대응** | 덱형 N장 → PDF N페이지. 오늘 6→4 로 어긋났다 |
| **V4 압축 신고** | 덱형이 버린 항목을 빠짐없이 신고한다. 문서형의 절·표 행 수와 대조 |
| **V5 금지 준수** | 산출물이 규격의 `금지` 를 어기지 않는다 |

V2 는 사람이 눈으로 봐야 한다. 이 세션에서 브라우저 자동화가 세 번 실패해 **생성물을 화면으로 확인하지 못한 채** 넘어간 적이 있다 — 그 상태를 "확인했다"로 적지 않는다.

## §8 범위 밖

- **HTML → PPTX · Word** (번역 변환). pantograph 가 등장하는 지점이며 별도 슬라이스
- **입력측** — PDF·이미지·워드에서 내용 꺼내기. 별개 문제
- **나머지 형식 9종** — 발표자료 · 제안서 · 소개서 · 개발문서 · 사용자 매뉴얼 · 회의록 · 장애 보고 · 요구사항 정의 · 릴리스 노트. 보고서 관통이 끝난 뒤 §4 의 여섯 필드로 복제한다
- **덱 시스템 스펙 보강** — §3.1 의 껍데기 누락은 덱 스펙에도 있다. 문서 시스템을 마친 뒤 같은 절을 덱 스펙에 더한다

## §9 형식 목록 — 확정

사용자 제시 6종에 넷을 더한다. 골격이 실제로 다른 것만 넣었다.

| 형식 | 대상 축 |
|---|---|
| 보고서 | 경영진 / 실무자 |
| 발표자료 | 청중의 사전 지식 |
| 제안서 | 제출처 |
| 소개서 | 수신자 |
| 개발문서 | 초급 / 중급 / 상급 |
| 사용자 매뉴얼 | 초급 / 중급 / 상급 |
| **회의록** | 참석자 / 미참석자 |
| **장애 보고** | 경영진 / 엔지니어 |
| **요구사항 정의** | 내부 합의 — 제안서(외부 설득)와 목적이 다르다 |
| **릴리스 노트** | 사용자 / 개발자 |

변형으로 충분해 별도 형식으로 만들지 않은 것: 분석 리포트(보고서 변형) · API 레퍼런스(개발문서 변형) · 온보딩(매뉴얼 변형). 별도로 만들면 관리 비용만 는다.
