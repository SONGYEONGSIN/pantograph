# panto diff — 경로 단위 차이 측정

**날짜**: 2026-08-09
**상태**: 확정
**선행**: [다중 파트 + pptx](2026-08-08-multipart-design.md), [docx 왕복 무손실](2026-08-06-docx-roundtrip-design.md)

---

## 1. 왜 지금인가

README 의 핵심 주장은 **"재현은 생성 문제가 아니라 측정 문제다"** 인데, 지금 `panto` 에는 측정 명령이 없다. `dump`·`apply`·`tmpl` 뿐이다.

「다음 작업」 1번(벤치마크 임계 도출)과 2번(렌더→비교→보정 루프)이 둘 다 **"두 문서가 어느 경로에서 다른가"** 를 전제로 한다. 그 조각이 비어 있어 둘 다 시작할 수 없다.

## 2. 기존 비교를 재사용하지 않는 이유

`tmpl.Extract` 안에 비교 코드가 셋 있다 — `diffPartSet`·`diffStructure`·`diffMarkup`. 이름은 diff 지만 **동작은 게이트다**: 전부 첫 차이에서 `return` 하고, 구조·마크업 차이를 `structure_mismatch`·`nontext_diff` **에러**로 부른다. "이 문서들이 같은 양식인가"를 판정해 아니면 거절하는 코드다. 템플릿 추출에는 그게 맞다 — 양식이 다른 문서에서 뽑은 키는 의미가 없다.

diff 는 정반대를 원한다. **모든 차이를 끝까지 세고, 그것을 에러가 아니라 데이터로 낸다.**

재사용하는 것은 **판정 술어**다 — 무엇을 "다르다"로 칠 것인가(§8). 재사용하지 않는 것은 **제어 흐름**이다. 게이트 코드는 손대지 않는다. fail-fast 는 `tmpl` 에 맞는 동작이지 결함이 아니다.

## 3. 명령 표면

```
panto diff <expected> <actual> [--part <선택자>]
```

**비대칭이다.** README 역할 분담 표가 "경로·속성·**기대값·실제값**" 이라 부르므로, 첫 인자가 기대, 둘째가 실제다. 출력의 모든 항목이 이 어휘를 쓴다.

`--part` 는 본문 파트 비교 범위를 좁힌다. `dump` 와 같은 `parts.Document.Select`, 같은 세 갈래 거절 사유(`part_not_found`·`ref_not_found`·`part_not_scannable`)를 쓴다. 선택자는 **expected 에 대해** 푼다 — 기대가 기준이므로 무엇을 비교할지는 기대가 정한다.

**선택자를 하나라도 주면 계획 밖 파트 비교(§5)를 통째로 건너뛴다.** 슬라이드 하나를 물었는데 레이아웃 16개 이야기를 듣는 것은 답이 아니다. 대신 그때의 "차이 없음" 은 **"이 파트에 차이 없음"** 이지 "재현됐음" 이 아니다 — 선택자를 준 쪽이 범위를 좁힌 것이다.

### 종료 코드

**차이 유무와 무관하게 0이다.** 차이는 결과지 오류가 아니다.

이 저장소의 종료 코드 계약은 에이전트의 재시도 판단에 쓰인다 — 1은 "입력이 틀렸으니 재시도 말 것", 2는 "이 도구가 제 일을 못 했다"(spec §9). 여기에 "차이가 있다"는 세 번째 뜻을 섞으면 그 판단이 흐려진다. 게이트가 필요한 소비자는 `summary.total` 을 본다. `--fail-on-diff` 는 필요해지면 그때 붙인다.

**단 포맷이 다르면 코드 1** (`format_mismatch`) 이다. docx 와 pptx 를 비교하는 것은 차이가 아니라 무의미한 입력이다.

## 4. 구조가 다를 때 — 위치 정렬, 갈리면 그 파트만 중단

> **이 절은 [LCS 정렬 설계](2026-08-10-lcs-align-design.md)가 대체했다.** 아래는 그 이전의 결정이며, "갈리면 그 파트만 중단" 은 더 이상 구현의 동작이 아니다. 기록으로 남긴다.

`tmpl.Extract` 는 노드 수가 다르면 즉시 문서 전체를 거절한다. diff 는 그럴 수 없다 — 보정 루프에서는 **재현물이 문단을 하나 더 갖거나 덜 갖는 것이 정상 상황**이고, 거절하면 가장 필요한 순간에 못 쓴다.

그래서 위치 정렬(index 대 index)로 비교하되, 경로가 갈리는 지점에서 `structure` 항목 **하나**를 내고 **그 파트만** 멈춘다. 다른 파트는 계속 본다.

LCS 정렬(삽입·삭제·변경 구분)은 하지 않는다 — README 「다음 작업」 4번으로 이미 분리돼 있다. 이 설계는 정렬기를 갈아끼울 자리를 남긴다: 노드 쌍을 만들어내는 부분만 교체하면 나머지 비교는 그대로 쓴다.

## 5. 어디까지 보는가

### 본문 파트 — 항상 스캔한다

바이트가 같아도 스캔해서 노드별로 비교한다. **바이트 같으면 건너뛰는 지름길을 넣지 않는다** — 넣으면 D1(자기 비교)이 비교 코드를 한 줄도 통과하지 않아, 통과하는데 아무것도 검증하지 않는 테스트가 된다. 본문 파트는 많아야 슬라이드 수만큼이라 비용이 문제되지 않는다.

### 계획 밖 파트 — 바이트로 거르고, 다를 때만 스캔한다

`dump`·`apply` 는 본문 파트만 본다. 재현 측정에서 그대로 두면 구멍이다 — 재현물이 `styles.xml` 이나 `slideLayout1.xml` 을 틀리게 써도 본문 노드는 전부 일치할 수 있고, 그러면 diff 가 **"차이 없음"** 이라고 말한다. 거짓 성공이다.

그래서 계획 밖 파트도 덮되, 3단으로 거른다:

1. **압축 해제 후 바이트 비교.** 같으면 끝 — 항목 없음. 압축 바이트로 비교하지 않는 이유: 그건 "인코딩이 다르다"를 "내용이 다르다"로 말하게 되어, 다른 생산자가 같은 내용을 다르게 압축하면 전부 거짓 양성이 된다
2. **다르면 그 파트만 스캔**해서 본문과 **같은 규칙**으로 비교한다. 루트 별칭은 루트 요소의 로컬명이다(multipart 스펙이 통일한 규약). 휘발성 차이뿐이면 항목이 하나도 안 나온다
3. **스캔이 안 되면**(바이너리, 파싱 실패) `part_content` 항목 하나로 내린다. 그 파트는 "다르다"까지만 말한다

주 용도(원본 vs panto 가 패치한 것)에서는 I2(국소성)가 계획 밖 파트의 바이트 동일을 보장하므로 **1단에서 전부 걸러지고 스캔은 0번 일어난다.** 스캔 비용은 독립 작성된 두 문서를 비교할 때만 발생하며, 그때도 압축 해제 전체가 `form-a` 65,621 B / `deck-a` 105,503 B 다.

### 이 3단이 실제로 무엇을 거르는가 (실측)

| 비교 | 전체 파트 | 본문 | 계획 밖 바이트 다름 | → 휘발성만 (항목 0) | → 진짜 차이 | → 스캔 불가 |
|---|---|---|---|---|---|---|
| `form-a` vs `form-b` | 11 | 1 | 3 | **1** (`word/styles.xml`) | 2 (`docProps/app.xml`, `word/settings.xml`) | 0 |
| `deck-a` vs `deck-b` | 41 | 3 | 16 | **12** (레이아웃 11 + 마스터 1) | 3 (`docProps/app.xml`, `docProps/core.xml`, `ppt/presentation.xml`) | 1 (`docProps/thumbnail.jpeg`) |

2단이 deck 의 노이즈 16개를 4개로, form 의 3개를 2개로 줄인다. 지우는 것이 **우리가 이미 아는 부류**라서 가능하다 — 그냥 바이트만 봤다면 슬라이드 레이아웃 11개와 마스터가 전부 "다르다"로 나왔을 것이고, 그중 실제 내용 차이는 **하나도 없다.**

남은 것은 전부 진짜다: `presentation.xml` 은 deck-a 에만 안내선(`p:extLst`)이 있고, `docProps/app.xml` 은 단어 수가 다르며(17 vs 15), `settings.xml` 은 설정이 실제로 다르다.

## 6. 차이 어휘

| kind | 뜻 | 항목이 싣는 것 |
|---|---|---|
| `text` | 요소가 **직접** 품은 텍스트가 다르다 (`w:t`·`a:t` 만이 아니다 — `<Words>17</Words>` 도 여기 걸린다) | scope, part, path, expected, actual |
| `attr` | 속성 값이 다르다 / 한쪽에만 있다 | scope, part, path, attr, expected, actual |
| `elem` | 같은 위치의 요소 타입이 다르다 | scope, part, path, expected, actual |
| `structure` | 경로 순열이 갈렸다 — 이 파트는 여기서 중단 | scope, part, path, detail |
| `part_content` | 스캔할 수 없는 파트의 내용이 다르다 | part, detail |
| `part_missing` | 한쪽에만 있는 파트 | part, detail |

`scope` 는 `"body"`(계획에 든 본문 파트) 또는 `"other"`(계획 밖) 다. 파트 이름만으로도 알 수 있지만, 소비자가 계획을 따로 들고 있어야 알 수 있는 것을 항목이 스스로 말하게 한다.

`part_missing` 은 본문·계획 밖을 가리지 않는다 — 한쪽에만 있는 파트는 어느 쪽이든 항목이 된다.

**네임스페이스 선언(`xmlns:w=…`)은 비교에서 뺀다.** `xmlscan.Attr` 은 그것을 일반 속성으로 담지만(스캐너 주석이 직접 경고한다) 내용이 아니다 — 같은 네임스페이스를 다른 접두사로 선언한 두 파일은 XML 로서 같다. `NS == "xmlns"` 인 항목을 거른다. 이 제외는 `diff` 안에만 둔다: `tmpl` 의 게이트까지 바꾸면 지금까지 거절하던 문서가 통과하게 되어 이 슬라이스 밖의 동작이 변한다.

`attr` 는 게이트보다 낫게 만든다. 게이트는 "속성 수가 다르다" 한 줄로 끝냈지만, diff 는 **속성 이름의 합집합**을 돌며 다른 것마다 항목을 하나씩 낸다. 한쪽에만 있는 속성은 없는 쪽 값을 `null` 로 싣는다.

## 7. 출력

```json
{
  "expected": "deck-a.pptx",
  "actual": "deck-b.pptx",
  "summary": {
    "text": 11, "attr": 0, "elem": 0, "structure": 1,
    "part_content": 1, "part_missing": 0,
    "total": 13, "volatile_only": 12
  },
  "diffs": [
    {
      "kind": "text", "scope": "body",
      "part": "ppt/slides/slide1.xml",
      "path": "sld/cSld[1]/spTree[1]/sp[1]/txBody[1]/p[1]/r[1]/t[1]",
      "expected": "표지", "actual": "겉표지"
    },
    {
      "kind": "part_content",
      "part": "docProps/thumbnail.jpeg",
      "detail": "스캔할 수 없어 내용만 비교했다 — 다르다 (길이 1741 B vs 1938 B)"
    }
  ]
}
```

`diffs` 는 발췌다. `summary` 는 이 두 픽스처의 전체 결과이며, `text` 11 은 본문 슬라이드 3 + `docProps/app.xml` 5 + `docProps/core.xml` 3 이다 (§10 의 표).

`volatile_only` 는 **바이트는 다른데 항목이 하나도 안 나온 계획 밖 파트의 수**다. 이 값이 없으면 사용자가 `unzip`+`diff` 로 본 것과 `panto diff` 의 답이 어긋나 보이고, 그 침묵을 설명할 방법이 없다. 12 라고 말해주면 "우리가 알고 무시했다"가 된다.

**순서**: `scope: "body"` 항목이 먼저, 계획 밖 항목이 뒤다. 본문 항목은 계획 순서(pptx 는 `sldIdLst` 순서)를, 파트 안에서는 노드 순서를 따른다. 계획 밖 항목은 파트 이름 사전순이다. 계획 밖 항목이 본문 항목보다 많을 수 있어서(§5 실측), 사람이 먼저 봐야 할 것을 앞에 둔다.

결정론적이다 — 같은 두 입력이면 항상 같은 바이트가 나온다 (I3 와 같은 근거).

## 8. 휘발성 — 세 번째 메커니즘이 필요하다

지금 모델은 둘이다:

- `VolatileAttrs` — 속성 **로컬명**으로 전역 제외 (`paraId`, `textId`, `rsid*`)
- `VolatileElements` — 그 **요소의 속성을 통째로** 제외 (`creationId`)

계획 밖 파트를 비교하기 시작하면 이 둘로 안 되는 것이 나온다.

```xml
<a:fld id="{2A621118-2E33-1746-9985-973F71BF27EF}" type="datetimeFigureOut">
```

날짜·슬라이드 번호 필드다. **`id` 는 문서마다 다르고 `type` 은 의미가 있다.** `id` 를 `VolatileAttrs` 에 넣으면 `p:cNvPr id="5"` 같은 실제 도형 정체성까지 눈이 멀고(multipart 스펙 §8 이 같은 이유로 `id` 전역 제외를 거부했다), `fld` 를 `VolatileElements` 에 넣으면 `type` 이 함께 사라져 날짜 필드와 슬라이드 번호 필드를 구별하지 못한다.

`word/settings.xml`·`word/styles.xml` 의 `<w:rsid w:val="005A4B1B"/>` 도 같은 모양이다 — 속성 이름이 `val` 이라 `rsid*` 접두 규칙에 안 걸린다.

그래서 **`VolatilePairs` — (요소 로컬명, 속성 로컬명) 짝** 을 더한다:

```go
var VolatilePairs = map[[2]string]bool{
    {"fld", "id"}:      true,  // a:fld — 날짜·슬라이드 번호 필드의 식별자
    {"rsid", "val"}:    true,  // w:rsid — Word 개정 저장 ID
    {"rsidRoot", "val"}: true, // w:rsidRoot — 같은 부류
}
```

이 셋은 실측으로 나온 것이지 예상 목록이 아니다. §5 표의 "휘발성만 13개"가 그 근거다.

### 휘발성 지식을 `tmpl` → `parts` 로 옮긴다

세 규칙이 지금 `internal/tmpl/schema.go` 에 있다. 이것들은 **형식 지식**이다 — `paraId`·`rsid*` 는 Word, `creationId`·`fld` 는 PowerPoint 다. multipart 스펙이 "`internal/parts` 가 형식 지식의 유일한 보관처" 라고 선언했으므로 지금 위치가 그 규칙과 어긋나 있다.

복제하지 않고 옮기는 이유: 진실이 둘이 되면 갈라지는 날이 오고, 그날 **I4a 와 diff 가 같은 문서에 서로 다른 답을 낸다.** 무엇이 휘발성인가는 한 곳에서만 정한다.

`VolatilePairs` 를 더하면 **`tmpl` 의 동작도 바뀐다** — 본문 파트에 `a:fld` 나 `w:rsid` 가 있는 문서에서 지금은 `nontext_diff` 로 거절하던 것이 통과하게 된다. 현재 픽스처의 본문 파트에는 `a:fld` 가 0개라 I4a 는 영향받지 않지만(실측), 이것은 의도된 개선이지 부작용이 아니다 — 그 차이는 원래 가변부가 아니었다.

**최종 리뷰가 실측으로 확인한 2차 효과**: 위 문단은 "속성이 사라진다"만 논했지, 그 속성이 사라진 자리에서 **자식 `a:t` 가 가변부 판별에 새로 노출된다**는 점은 안 짚었다. `id` 만 다르고 자식 텍스트도 같은 `a:fld` 라면 `diffMarkup` 이 속성 단계에서 더 볼 것 없이 넘어가고, 그 아래 `a:t` 는 원래도 일반 텍스트 노드라 계속 순회 대상이었다 — 두 문서의 슬라이드 번호 텍스트("1" 대 "7")가 다르면 그것도 하나의 가변 키가 된다. 실측: merge-base(`5f79930`)에서 본문에 `a:fld id="{AAAA…}" type="slidenum"><a:t>1</a:t>` (fld-a) vs `id="{BBBB…}"><a:t>7</a:t>` (fld-b) 인 합성 슬라이드 한 쌍을 돌리면 `nontext_diff` 로 거절됐다(`속성 id: fld-a.pptx 는 "{AAAA…}", fld-b.pptx 는 "{BBBB…}"`). 같은 입력을 HEAD(`573116c`)에서 돌리면 `ok: true` 로 통과하고 스키마에 키가 하나 더 생긴다 — `part: ppt/slides/slide1.xml`, `path: sld/cSld[1]/spTree[1]/sp[1]/txBody[1]/p[1]/fld[1]/t[1]`, `samples: ["1", "7"]`. 즉 PowerPoint 가 렌더 시 재생성하는 슬라이드 번호·날짜 필드 안에 `{{k}}` 구멍이 뚫린다.

**I4a 는 그럼에도 깨지지 않는다** — 이유가 구조적이다. `tmpl.Fill` 이 만드는 템플릿 문서는 base 문서의 **원본 바이트에 `setText` 패치만 얹은 것**이라, base → 템플릿 추출 → (같은 데이터로) 채움 → base 왕복은 애초에 어떤 경로가 가변부로 뽑히든 항등이다. 가변부 판별이 넓어지거나 좁아지는 것은 "무엇을 키로 뽑았는가"에만 영향을 주지, 뽑힌 키를 원래 값으로 되채웠을 때 바이트가 같아지는지에는 영향을 주지 않는다.

**주의할 점**: `a:fld` 가 본문에 있는 문서에서 템플릿을 뽑을 때는, 그 필드의 자식 텍스트가 **문서 저장 시점에 PowerPoint 가 굳혀 넣은 스냅샷**(예: "1"쪽·"7"쪽처럼 당시 슬라이드 번호)이라는 점을 알고 있어야 한다. 여러 벌의 문서에서 이 값이 우연히 다르면 그것이 진짜 가변부(사용자가 채워 넣을 자리)로 뽑히지만, 실제로는 "이 필드가 렌더될 때 PowerPoint 가 다시 계산해서 덮어쓰는 값"이라 `panto` 로 되채워도 오피스가 열면서 갱신해버릴 수 있다. `--part` 로 좁혀 뽑거나, 추출된 스키마에서 `type` 이 `slidenum`/`datetimeFigureOut` 인 `fld` 밑의 키를 사람이 검토해 걷어내는 것이 안전하다.

## 9. 아키텍처

### 새 패키지 `internal/diff`

```go
// Compare 는 두 문서의 차이를 끝까지 센다. 에러를 내는 것은 비교 자체가 불가능할 때뿐이다.
func Compare(expected, actual *parts.Document, sels []string) (*Report, error)
```

`tmpl` 을 import 하지 않는다. `tmpl` 도 diff 도 기능 계층이라, 한쪽이 다른 쪽을 부르면 나중에 어느 쪽이 규칙의 주인인지 알 수 없게 된다. 공유하는 것은 `parts` 에 있다.

### `Document.Bytes(name)` 추가

계획 밖 파트의 내용을 읽을 길이 지금 없다 — `Document` 는 `Names()`·`Tree()` 만 준다. `Bytes` 는 `opc.Package.Part` 로 위임하며, 그 경로가 이미 미지원 압축 방식과 폭탄 가드를 다룬다.

### `Document.ScanAny(name)` 추가

계획 밖 파트를 스캔한다. `Tree` 는 계획에 든 파트만 받고 루트 별칭을 계획에서 가져오는데, 계획 밖 파트에는 그 값이 없다. `ScanAny` 는 **루트 요소의 로컬명**을 별칭으로 써서 스캔하고, 파싱 실패는 에러로 돌려준다(호출자가 `part_content` 로 내린다). 결과는 `Tree` 와 같은 캐시에 담지 않는다 — 계획 밖 파트는 계획의 일부가 아니다.

## 10. 불변식

| | 이름 | 내용 |
|---|---|---|
| **D1** | 자기 비교 | 같은 파일을 두 번 주면 `diffs` 가 비고 `volatile_only` 도 0 이다 |
| **D2** | 교차 검증 | `text` 항목이 `tmpl.Extract` 가 뽑은 키와 경로·값에서 정확히 일치한다 |
| **D3** | 국소성 | `apply` 로 한 파트만 고친 문서와 원본을 비교하면 그 파트의 `text` 항목만 나오고, 계획 밖 항목은 0 이다 |

**D1 에 해시 지름길을 넣지 않는다** (§5). 두 파일의 해시가 같으면 순회 없이 빈 리포트를 낼 수 있지만, 그러면 D1 이 아무것도 검증하지 않는다.

**D2 는 독립적으로 짠 두 코드 경로가 같은 답을 내는지 보는 검사다.** 기준값(실측):

| 비교 | 키 | 경로 | 기대 → 실제 |
|---|---|---|---|
| form | k1 | `document/body[1]/p[2]/r[2]/t[1]` | `: 홍길동` → `: 김철수` |
| | k2 | `document/body[1]/p[3]/r[2]/t[1]` | `: 1,200,000` → `: 880,000` |
| | k3 | `document/body[1]/p[4]/r[2]/t[1]` | `: A & B 프로젝트` → `: C & D 프로젝트` |
| deck | k1~k3 | `sld/cSld[1]/spTree[1]/sp[1]/txBody[1]/p[1]/r[1]/t[1]` (슬라이드 1·2·3) | `표지`→`겉표지`, `둘째 장`→`두번째쪽`, `셋째 장`→`마지막쪽` |

### 전체 항목 수 (독립 측정)

아래는 **Go 구현이 아니라 파이썬으로 따로 짠 비교기**가 낸 수다. 구현이 이 수와 다르게 나오면 **수를 고치지 말고 차이를 설명해야 한다** — 둘 중 하나가 틀렸다는 뜻이고, 구현이 낸 값을 그대로 받아적으면 테스트가 구현의 거울이 되어 아무것도 검증하지 않는다.

그 비교기는 `docs/superpowers/specs/oracle/diff-count.py` 에 있다(저장소 루트에서 `python3 docs/superpowers/specs/oracle/diff-count.py`로 재현). **한계**: 파이썬 `xml.etree` 는 네임스페이스 선언·속성의 네임스페이스를 xmlscan 과 다르게 다뤄, 이 오라클은 속성을 로컬명만으로 비교한다 — 그래서 최종 리뷰가 찾은 attrMap 의 네임스페이스 충돌 결함을 이 오라클도 똑같이 못 잡는다(픽스처의 `sldId`/`sldLayoutId` 값이 두 파일에서 같아 우연히 드러나지 않았을 뿐이다). 스크립트 머리말에 이 한계와 `.text`/`.tail` 모델 차이를 더 자세히 적어 뒀다.

**아래 수치는 [LCS 정렬 설계](2026-08-10-lcs-align-design.md) 이후 값이다.** 그 이전(위치 정렬) 값은 deck 행 기준 `structure 1`·`deleted 0` 이었다 — 총량(`total`·`volatile_only`)은 안 바뀌고 deck 의 `ppt/presentation.xml` 차이 1건이 `structure` 에서 `deleted` 로 종류만 바뀐다(LCS 설계 §7 의 예측대로다).

| | `text` | `attr` | `elem` | `structure` | `inserted` | `deleted` | `part_content` | `total` | `volatile_only` |
|---|---|---|---|---|---|---|---|---|---|
| form-a vs form-b | 5 | 2 | 0 | 0 | 0 | 0 | 0 | 7 | 1 |
| deck-a vs deck-b | 11 | 0 | 0 | 0 | 0 | 1 | 1 | 13 | 12 |

내역:

| 비교 | 파트 | scope | 항목 |

| | `word/settings.xml` | other | `attr` 2 |

**D3 가 §5 의 노이즈 주장을 증명한다.** 주 용도에서 계획 밖 항목이 0 이라는 것이 말이 아니라 테스트여야 한다.

구조 차이와 `part_missing` 은 합성 컨테이너로 만든다 — 실제 픽스처에 그런 쌍이 없다.

## 11. 알려진 한계

- **런 분할에 취약했다 — [LCS 정렬 설계](2026-08-10-lcs-align-design.md)가 절반만 갚았다.** `<w:t>안녕</w:t><w:t>하세요</w:t>` 와 `<w:t>안녕하세요</w:t>` 는 보이는 텍스트가 같아도 노드 수가 달라 여전히 "같다"로 보지 않는다. 다만 이제는 그 파트를 통째로 포기하지 않고 어디가 다른지(`inserted`/`deleted`)는 짚는다 — 위치는 짚지만 텍스트 수준의 동등성은 별개 문제로 남는다. 진짜 해결(런 병합 정규화)은 그 설계 §9 가 범위 밖으로 미뤘다
- **더 이상 참이 아니다.** `structure` 이후 그 파트의 남은 노드는 비교되지 않는다던 문장은 위치 정렬 시절의 동작이다. [LCS 정렬 설계](2026-08-10-lcs-align-design.md) 이후 `structure` 는 상한 초과 또는 빈 파트로만 좁혀졌고, 그 두 경우가 아니면 정렬은 포기 없이 끝까지 비교한다
- **스캔 불가 파트는 "다르다"까지만** 말한다 (`docProps/thumbnail.jpeg` 같은 바이너리). 이미지가 바뀐 것과 1픽셀이 바뀐 것을 구별하지 않는다
- `VolatilePairs` 는 **관찰된 것의 목록이지 완전한 목록이 아니다.** 다른 생산자·다른 버전이 우리가 모르는 휘발성 식별자를 쓰면 그것은 진짜 차이로 보고된다. 새 픽스처가 들어올 때마다 이 목록이 자란다
- 문자 참조 인코딩 한계(docx 스펙 §13)를 그대로 물려받는다. `Text` 는 디코드된 값이므로 `&#38;` 와 `&amp;` 는 **같다고** 판정된다 — 템플릿 채우기와 반대 방향의 비대칭이다
