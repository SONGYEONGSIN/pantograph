# LCS 정렬 — 구조가 다른 문서를 포기하지 않고 비교한다

**날짜**: 2026-08-10
**상태**: 확정
**선행**: [경로 단위 차이 측정](2026-08-09-diff-design.md) (이 슬라이스가 그 §4 를 대체한다)

---

## 1. 왜 — 포기하기 전에 거짓말을 한다

diff 설계 §11 은 이 한계를 "런 분할에 취약하다 · 구조가 갈리면 그 파트를 포기한다" 로 적었다. 실측해 보니 **더 나쁘다. 포기하기 전에 거짓말을 한다.**

문단을 가운데 하나 삽입한 두 문서를 비교하면:

```
text  document/body[1]/p[2]/r[1]/t[1]   expected='셋째 줄'  actual='새로 낀 줄'
structure  document/body[1]/p[3]        노드 수가 다르다 — 기대 8개, 실제 11개
```

**아무도 `셋째 줄` 을 `새로 낀 줄` 로 바꾸지 않았다.** 문단이 하나 끼어들어 뒤가 밀렸을 뿐이다. 이 출력을 믿는 에이전트는 `p[2]` 를 `셋째 줄` 로 되돌리는 패치를 쓴다 — 정확히 틀린 수정이다.

원인은 위치 정렬(index 대 index)이다. 삽입이 일어나면 그 뒤의 모든 노드가 서로 다른 것과 짝지어진다. 경로도 함께 밀린다 (실측: `셋째 줄` 이 `p[2]` → `p[3]`).

이 저장소는 조용한 실패를 가장 심각한 결함으로 본다. **자신 있게 틀린 말을 하는 것은 그보다 나쁘다.**

## 2. 무엇으로 정렬하는가 — 실패한 후보들

프로토타입으로 세 가지를 재봤다. 앞의 둘은 **쓸 수 없다**:

| 후보 | 결과 |
|---|---|
| **경로(`Path`)** | 삽입 지점 이후로 같은 경로가 서로 다른 내용을 가리킨다. 정렬 키로 성립하지 않는다 |
| **평평한 LCS, 키 = 요소 타입** | 서브트리는 깔끔히 떨어지지만 **엉뚱한 문단을 삽입이라 한다.** `p[2]` 에서는 여전히 `셋째 줄 → 새로 낀 줄` 이라는 같은 거짓말을 낸다 — 고치려던 것을 못 고친다 |
| **평평한 LCS, 키 = 타입+텍스트** | 의미는 맞지만 삽입 구간이 `t('새로 낀 줄'), p[3], r[1]` 로 나온다 — **서브트리가 아니다.** 한 문단의 `t` 와 다음 문단의 `p`·`r` 을 걸쳐 자른다. 접을 수 없다 |

마지막이 트리를 평평하게 눌러 LCS 를 돌릴 때의 고전적 함정이다: 정렬이 서브트리 경계를 넘나든다.

## 3. 알고리즘 — 형제 목록마다 계층 LCS

트리 편집 거리를 풀지 않는다. **형제 목록 단위로만** LCS 를 돌리고 매칭된 쌍으로 재귀한다.

```
align(A, B):                     # A·B 는 같은 부모의 자식 목록
  1. 서브트리 해시로 앞뒤 공통 구간을 잘라낸다
  2. 남은 구간에 LCS (키 = 서브트리 해시)
       equal   → 통째로 같다. 내려가지 않는다
       insert  → B 쪽 서브트리마다 inserted 1건
       delete  → A 쪽 서브트리마다 deleted 1건
       replace → 양쪽에 남았다. 위치로 짝짓고 각 쌍을 compare 로 재귀
                 (짝이 없는 꼬리는 insert/delete)

compare(a, b):                   # 짝지어진 노드 한 쌍
  타입·직접 텍스트·속성을 비교해 elem/text/attr 항목을 낸다
  align(a.kids, b.kids)
```

**`replace` 분기가 D2 를 살린다.** 텍스트만 바뀐 문단은 서브트리 해시가 달라 LCS 매칭에 실패하지만, 같은 구간에 양쪽 다 남아 있어 위치로 짝지어지고, 재귀하면 그 안에서 `text` 차이를 정확히 찾는다. 이 규칙이 없으면 기존 D2 결과가 전부 삭제+삽입 쌍으로 바뀐다.

**`equal` 구간은 내려가지 않는다.** 같은 부분은 아예 순회하지 않는다는 뜻이라 부수적으로 빨라진다.

### 서브트리 해시

요소 타입 + 직접 텍스트 + 안정 속성 + 자식들의 해시.

**안정 속성이란**: `parts.StableAttrs` 를 통과하고 `NS == "xmlns"` 가 아닌 것 — 본문 비교와 **정확히 같은 규칙**이다. 휘발성이 해시에 들어가면 **pptx 레이아웃은 영영 매칭되지 않는다**. `creationId` 가 문서마다 다르기 때문이다.

### 부모·자식 관계

`xmlscan` 은 평평한 pre-order 를 준다. 부모·자식은 **`Span` 포함 관계**로 구한다 — pre-order 에서 노드 `i` 의 서브트리는 `Span` 이 `Span[i]` 안에 들어가는 뒤쪽 연속 구간이다.

경로 문자열 접두사(`부모 + "/"`)로도 되고 `p[1]/` 이 `p[10]` 과 헷갈리지도 않지만, `Span` 이 이미 있고 모호함이 없다.

## 4. 어휘

`structure` 가 뜻하던 **"여기서 갈렸고 이후는 포기했다"** 는 사라진다. 포기하는 일이 없어지기 때문이다.

| kind | 뜻 | 항목이 싣는 것 |
|---|---|---|
| `inserted` | 실제에만 있는 서브트리 | scope, part, path(**실제 기준**), detail(노드 수) |
| `deleted` | 기대에만 있는 서브트리 | scope, part, path(**기대 기준**), detail(노드 수) |
| `structure` | **정렬을 포기하고 위치로 비교했다** (§5 상한 초과) | scope, part, path, detail |

`text`·`attr`·`elem`·`part_content`·`part_missing` 은 그대로다.

**`elem` 이 처음으로 도달 가능해진다.** 위치 정렬에서는 짝지어진 두 노드의 경로가 이미 같아야 했고 경로가 타입을 포함하므로 타입이 다를 수 없었다 — diff 의 최종 리뷰가 `elem` 을 "도달 불가능한 선반영 코드" 로 지목했다. `replace` 구간의 위치 짝짓기는 경로를 요구하지 않으므로, 같은 자리의 서로 다른 요소가 이제 `elem` 으로 나온다.

`structure` 라는 이름을 새 단어로 대체하지 않고 **상한 전용으로 좁힌다.** 어휘를 하나 더 만들지 않으면서 옛 뜻은 없앤다. 실제 문서에서는 사실상 나오지 않는 이름이 된다.

**순수 이동은 보고하지 않는다.** 삽입 케이스에서 `셋째 줄` 문단이 `p[2]`→`p[3]` 로 밀렸지만 항목은 0건이다. 왜 경로가 밀렸는지는 `inserted` 항목이 이미 설명한다. 이동을 별도 항목으로 내면 문단 하나 삽입에 그 뒤 전부가 "이동" 으로 딸려 나온다.

**`inserted`/`deleted` 는 서브트리당 1건이다.** 문단 하나는 노드 3개(`w:p`·`w:r`·`w:t`)이고 실제 문서에서는 10~20개다. 노드마다 항목을 내면 문단 하나에 수십 줄이 된다. `detail` 에 노드 수를 실어 무게를 알린다.

## 5. 증폭 방어

DP 표가 형제 수의 곱이다. **실측 형제 수**: `form-a` 최대 376개(`word/styles.xml` 의 `latentStyles`), `deck-a` 최대 50개. 노드 대부분은 자식이 1개 이하다(form 1220개 중 1081개).

376×376 = 14만 칸으로 무해하지만 1만×1만은 1억 칸(`int32` 로 400MB)이다. `plan.go` 가 이미 막아둔 증폭 공격과 같은 부류다 — 입력 XML 이 작업량·메모리를 곱으로 부풀리는 지점.

- **앞뒤 공통 구간을 먼저 잘라낸다.** 실제 문서는 대부분 여기서 해결된다
- 남은 곱이 **4,000,000**(`int32` 로 16MB)을 넘으면 그 형제 목록만 위치 정렬로 떨어지고 **`structure` 항목으로 그 사실을 알린다.** 조용히 떨어지면 그게 거짓 성공이다

상한은 형제 하나가 2000개까지는 정상 처리한다는 뜻이다 — 실측 최대치의 5배.

## 6. 불변식

| | 이름 | 내용 |
|---|---|---|
| **L1** | 삽입 정직성 | 문단 하나 삽입 → `inserted` **1건**. 거짓 `text` 항목이 **0건** |
| **L2** | D2 보존 | 기존 D2 전체 수가 유지된다 (§7 표) |
| **L3** | 기존 불변식 유지 | D1(자기 비교 0건)·D3(국소성)이 그대로다 |
| **L4** | 상한 정직성 | 상한을 넘으면 `structure` 항목을 내고 **그 파트를 계속 비교한다** |

**L2 가 이 슬라이스의 안전줄이다.** 정렬기를 갈아끼우면서 기존 답이 바뀌면 그것은 회귀다.

## 7. D2 가 어떻게 바뀌는가 (프로토타입 실측 + 예측)

프로토타입(파이썬, 위 알고리즘 그대로)으로 잰 값:

| 비교 | 본문 `text` 항목 | 판정 |
|---|---|---|
| 문단 삽입 쌍 | `inserted` 1건, `text` 0건 | L1 ✅ |
| `form-a` vs `form-b` | `text` 3건 — 경로·값 전부 기존 D2 와 일치 | L2 ✅ |
| `deck-a` vs `deck-b` | `text` 3건 — 슬라이드 1·2·3 정확 | L2 ✅ |

**전체 수의 예측** — 구현이 확인해야 한다:

| | 기존 | LCS 이후 | 근거 |
|---|---|---|---|
| form total / volatile_only | 7 / 1 | **7 / 1 (불변)** | 구조 차이가 없다 |
| deck total / volatile_only | 13 / 12 | **13 / 12 (불변)** | 총량은 같고 `structure 1` → `deleted 1` 로 종류만 바뀐다 |

deck 의 `structure 1` 은 `ppt/presentation.xml` 에서 났다. 실측 확인: `p:presentation` 의 자식이 deck-a 는 `[sldMasterIdLst, sldIdLst, sldSz, notesSz, defaultTextStyle, extLst]`, deck-b 는 `extLst` 가 없다. **`extLst` 는 최상위 자식이므로 `deleted` 정확히 1건**이 된다.

**프로토타입의 한계**: 파이썬 `difflib.SequenceMatcher` 로 쟀는데 그것은 고전적 LCS 가 아니라 Ratcliff-Obershelp 다(`autojunk=False` 로 둬도 마찬가지). Go 구현은 진짜 LCS DP 를 쓸 것이므로 **정렬이 갈릴 수 있다.** 프로토타입이 검증한 것은 **접근법**(형제 단위·서브트리 해시·`replace` 재귀)이지 특정 알고리즘의 출력이 아니다. 두 알고리즘 모두 "최장 공통 부분열" 을 찾지만 동점일 때 고르는 것이 다르다.

**구현이 다른 수를 내면 수를 고치지 말고 원인을 찾는다.** 파이썬 오라클(`docs/superpowers/specs/oracle/diff-count.py`)도 이 알고리즘을 반영하도록 함께 고친다 — 오라클이 옛 알고리즘을 재면 다음 라운드가 헛짚는다.

## 8. 아키텍처

`internal/diff` 안에 머문다. `parts`·`xmlscan`·`tmpl` 은 건드리지 않는다.

- **`internal/diff/align.go` (신규)** — 트리 구성(`Span` 포함), 서브트리 해시, 형제 LCS, 상한
- **`internal/diff/compare.go` (수정)** — `compareTrees` 가 위치 루프 대신 `align` 을 부른다. 노드 한 쌍의 비교(`elem`/`text`/`attr`)는 **그대로 쓴다** — 바뀌는 것은 짝을 만드는 방법뿐이다
- **`internal/diff/report.go` (수정)** — `Summary` 에 `Inserted`·`Deleted` 추가. `Structure` 는 남되 뜻이 좁아진다

diff 설계 §4 가 "정렬기를 갈아끼울 자리를 남긴다 — 노드 쌍을 만들어내는 부분만 교체하면 나머지 비교는 그대로 쓴다" 고 적었고, 그 예고가 맞았다.

## 9. 범위 밖

- **런 분할 인식** — `<w:t>안녕</w:t><w:t>하세요</w:t>` 와 `<w:t>안녕하세요</w:t>` 는 LCS 이후에도 "같다" 가 되지 않는다. **LCS 는 그것을 못 고친다** — 텍스트 수준의 동등성이지 구조가 아니다. 다만 "이 파트를 포기한다" 가 "런 2개가 삭제되고 텍스트가 바뀌었다" 로 바뀌어 **위치를 짚을 수는 있게** 된다. 진짜 해결은 런 병합 정규화이고 별도 슬라이스다. diff 설계 §11 이 이 항목을 README 「다음 작업」 4번으로 미룬 것을 여기서 **절반만** 갚는다
- **이동 검출** — 문단이 위아래로 옮겨간 것을 "이동" 이라 부르는 것. 지금은 삭제+삽입으로 나온다
- **템플릿 추출에 적용** (README 「다음 작업」 4번의 나머지 절반) — 같은 정렬기를 `tmpl.Extract` 에 물리는 일. 이 슬라이스는 `diff` 만 바꾼다. `tmpl` 의 게이트는 그대로 fail-fast 다
- **Hirschberg 등 공간 최적화** — 상한으로 충분하다. 필요해지면 그때
