# tmpl 정렬 — 구조가 다른 문서에서 템플릿을 뽑는다

**날짜**: 2026-08-11
**상태**: 확정
**선행**: [LCS 정렬](2026-08-10-lcs-align-design.md) (정렬기를 만든 슬라이스), [경로 단위 차이 측정](2026-08-09-diff-design.md)

---

## 1. 왜 — 두 명령이 같은 문서에 다른 말을 한다

LCS 정렬은 `diff` 에만 들어갔다. 같은 두 문서에 대해:

```
panto diff         x.docx y.docx  →  text 2 · structure 1 · inserted 1   (어디가 다른지 짚는다)
panto tmpl extract x.docx y.docx  →  structure_mismatch                  (문서 전체를 거절)
```

정렬기는 이미 `internal/diff/align.go` 에 있고 `tmpl` 이 못 쓸 뿐이다. README 「다음 작업」 4번이 말하는 "구조가 다른 문서 간 템플릿 추출" 의 나머지 절반이다.

## 2. 진짜 문제는 정렬이 아니라 표현 가능성

**정렬기를 물리는 것만으로는 안 된다.** 템플릿의 표현력이 먼저 걸린다.

템플릿은 **base 의 바이트에 `setText` 를 얹은 것**이다(`extract.go` 3단계). `patch` 의 연산은 `setText` 와 `replaceRaw` 둘뿐이다. 그래서 템플릿이 표현할 수 있는 것은 **"이 자리의 텍스트가 문서마다 다르다"** 하나뿐이고, **"이 문단은 어떤 문서에는 있고 어떤 문서에는 없다"** 를 담을 수단이 없다.

정렬에 성공해도 그 다음이 막힌다:

- base 에만 있는 문단 → 템플릿에 그대로 남는다. 그 문단이 없는 문서를 이 템플릿으로 재현할 수 없다
- base 에 없고 다른 문서에만 있는 문단 → **템플릿에 자리가 없다.** 그 내용은 표현 불가능하다

**결정**: 모든 문서에서 **매칭된 부분에서만** 가변 키를 뽑는다. 매칭되지 않은 서브트리는 키 후보에서 빼고 스키마의 `unrepresented` 에 **빠짐없이 남긴다**.

이 저장소가 이미 쓰는 패턴이다 — `diff` 의 `volatile_only` 가 "우리가 알고 무시했다" 를 밝히고, 파이썬 오라클 헤더가 "이 오라클은 이것을 못 잡는다" 를 고백한다. **도구가 자기가 못 하는 것을 스스로 말한다.**

## 3. `ok:true` 의 뜻을 지킨다

지금은 구조가 다르면 `Extract` 가 **실패**한다. §2 를 넣으면 **성공**하게 된다 — 단서가 붙은 성공이다.

**단서는 무시할 수 있지만 실패는 무시할 수 없다.** 이 저장소가 PR #3 을 통째로 쓴 이유가 그것이었다: `{"ok":true}` 를 내면서 데이터를 지우던 디코더.

그래서 **기본은 거절이다**. 표현 못 하는 것이 하나라도 있으면 `unrepresented_structure` 로 거절하고, `--allow-unrepresented` 를 준 경우에만 진행해 목록을 싣는다.

> **불변식: `ok:true` 는 "이 템플릿이 입력 전부를 표현한다" 를 계속 뜻한다.** 플래그를 준 경우만 예외이고, 그것은 사용자가 명시적으로 산 것이다.

`diff` 와 다르게 가는 이유가 분명하다. `diff` 는 **읽기 전용**이라 잘못 읽어도 문서가 망가지지 않아 "차이가 있어도 코드 0" 이 맞았다. `tmpl` 은 **산출물을 만들고 그 산출물이 나중에 문서를 생성한다** — 잘못된 템플릿은 조용히 퍼진다.

## 4. 정렬기를 `internal/align` 으로 옮긴다

`tmpl` 이 `diff` 를 import 하면 안 된다. diff 설계 §8 이 그 반대 방향을 이미 금지했다 — *"tmpl 도 diff 도 기능 계층이라, 한쪽이 다른 쪽을 부르면 나중에 어느 쪽이 규칙의 주인인지 알 수 없게 된다"* — 그 논거는 대칭으로 성립한다.

**패키지 그래프** (실측):

```
xmlscan  →  (내부 의존 없음)
parts    →  opc, xmlscan
align    →  parts, xmlscan          ← 신설
diff     →  align, opc, parts, patch, xmlscan
tmpl     →  align, opc, parts, patch, xmlscan
```

순환이 없다. `align` 은 `parts.StableAttrs` 를 쓰므로 `parts` 위에 선다.

**옮기는 것**: `node`·`buildTree`·`sign`·`stableAttrTriples`·`op`·`alignSiblings`·`alignMiddle`·`maxCells`, 그리고 **`attrMap`**. `attrMap` 은 지금 `diff/compare.go` 에 있는데 `sign`(해시)과 `compareAttrs`(비교)가 함께 쓴다 — **둘이 같은 규칙을 봐야 하므로 갈라놓을 수 없다.**

**순수 이동 + export 다. `diff` 의 동작이 한 톨도 바뀌면 안 된다.** D2(`form 7/1` · `deck 13/12`)가 그 안전줄이다 — 정렬기를 들어내면서 결과가 달라지면 그것은 회귀다.

## 5. `Extract` 의 2단계가 어떻게 바뀌나

```
현재:  diffStructure(경로 순열이 완전히 같아야 함)
         → diffMarkup(비텍스트 차이는 거절)
         → 가변부 판별(t 노드의 텍스트가 다르면 키)

이후:  align(base, doc[i]) — 형제 목록마다 LCS
         → 매칭된 쌍에만 diffMarkup
         → 가변부 판별
         → 매칭 안 된 서브트리는 unrepresented
```

### "매칭됐다" 가 무슨 뜻인가 — 이것이 T1 의 생사를 가른다

정렬 결과는 네 종류 구간을 낸다(`'e'`·`'i'`·`'d'`·`'r'`). **매칭은 `'e'` 와 `'r'` 둘 다다:**

| 구간 | 뜻 | tmpl 에서의 처리 |
|---|---|---|
| `'e'` | 서브트리가 통째로 같다 | 매칭. 다만 **키가 나올 수 없다** — 아무것도 다르지 않다 |
| `'r'` | 양쪽에 남아 **위치로 짝지어졌다** | 매칭. **키는 전부 여기서 나온다** |
| `'i'`·`'d'` | 한쪽에만 있다 | 매칭 아님 → `unrepresented` |

**`'r'` 을 매칭으로 안 보면 T1 이 즉시 깨진다.** `form-a` 대 `form-b` 의 문단들은 텍스트가 달라 서브트리 해시가 다르고, 따라서 `'e'` 가 아니라 `'r'` 구간에 들어간다. `'r'` 을 빼면 **키가 하나도 안 나온다** — 지금 뽑히는 `k1`~`k3` 가 전부 사라진다.

LCS 설계 §3 이 "`replace` 분기가 D2 를 살린다" 고 적은 것과 같은 사실이다. 거기서는 `text` 항목이, 여기서는 가변 키가 그 분기에서 나온다.

**규칙 셋:**

1. **가변 키 후보는 "모든 문서에서 매칭된" base 노드뿐이다.** `Extract` 는 base 를 각 문서와 따로 정렬하므로(`docs[0]` vs `docs[i]`), doc1 과는 매칭됐는데 doc2 와는 안 된 노드가 있을 수 있다. 그런 노드는 후보에서 뺀다 — 어느 문서의 값을 sample 로 삼을지 정할 수 없기 때문이다
2. **매칭된 노드에는 `diffMarkup` 의 엄격한 게이트를 그대로 유지한다.** 속성이 다르면 그것은 같은 양식이 아니다. 정렬은 "어느 노드끼리 비교할지" 만 바꾸지 "무엇을 차이로 볼지" 는 안 바꾼다
3. **`diffPartSet` 은 손대지 않는다.** 파트 집합이 다른 것은 슬라이드 수가 다르다는 뜻이고 multipart 스펙 §12 가 이미 미뤄뒀다. 이 슬라이스는 **파트 안쪽 구조**만 다룬다

## 6. 스키마 변화

```json
{
  "base": "a.docx",
  "hash": "sha256:…",
  "keys": [ … 기존 그대로 … ],
  "unrepresented": [
    {
      "doc": "b.docx",
      "part": "word/document.xml",
      "path": "document/body[1]/p[2]",
      "side": "b.docx 에만",
      "nodes": 3
    }
  ]
}
```

`unrepresented` 는 **비어 있으면 필드 자체가 나오지 않는다**(`omitempty`) — 구조가 같은 문서에서 뽑은 스키마는 지금과 바이트 동일해야 한다(§7 T1).

`side` 는 어느 쪽에만 있는지다 — base 에만 있으면 템플릿에 남아 그 문서를 재현할 때 **지워지지 않고**, 다른 문서에만 있으면 템플릿에 자리가 **없다**. 두 실패 모양이 다르므로 구분해서 싣는다.

**`Fill` 은 바꾸지 않는다.** 스키마를 받은 사람이 이미 플래그로 산 것이고 `Fill` 의 일은 기계적이다. 두 번째 게이트는 중복 마찰이다.

## 7. 불변식

| | 이름 | 내용 |
|---|---|---|
| **T1** | 무회귀 | 구조가 같은 문서에서는 **기존과 완전히 같은 결과**가 나온다 — 키·스키마·템플릿 바이트, I4a 포함 |
| **T2** | 기본 거절 | 구조가 다르면 플래그 없이 `unrepresented_structure` 로 거절한다 |
| **T3** | 빠짐없는 신고 | 플래그를 주면 공통부에서 키를 뽑고, 매칭 안 된 서브트리가 `unrepresented` 에 **빠짐없이** 실린다 |
| **T4** | diff 무회귀 | `diff` 의 D1·D2·D3 가 그대로 통과한다 — 정렬기 이동이 아무것도 안 바꿨다 |
| **T5** | 정렬 합치 | 같은 문서 쌍에서 `diff` 의 `inserted`·`deleted` 경로 집합과 `tmpl` 의 `unrepresented` 경로 집합이 **일치한다** |

**T5 가 필요한 이유**: `diff` 는 짝을 만들며 곧바로 항목을 뱉고(`alignChildren`), `tmpl` 은 짝 목록을 받아 나중에 판단한다 — 두 재귀가 같은 `Siblings` 위에 서지만 **`'r'` 구간의 위치 짝짓기 규칙이 각자에 복제된다.** 갈라지는 날 `diff` 와 `tmpl` 이 같은 문서에 다른 답을 내는데, 그것이 바로 이 슬라이스가 없애려던 상태다(§1). 구조로 막는 대신 **테스트로 잠근다** — 두 명령을 같은 합성 쌍에 돌려 경로 집합을 대조한다.

**T1 과 T4 가 이 슬라이스의 안전줄이다.** 현재 픽스처(`form-a`/`form-b`, `deck-a`/`deck-b`)는 전부 구조가 같으므로 기존 테스트가 **그대로** 통과해야 한다. 구조가 다른 쌍은 합성으로 만든다 — 실제 픽스처에 그런 쌍이 없다.

**T3 의 "빠짐없이" 를 어떻게 시험하는가**: 합성 문서 쌍에서 매칭 안 된 서브트리 수를 **정렬 결과로부터 독립적으로** 세어(문서를 만들 때 몇 개를 넣었는지 알고 있다) `unrepresented` 항목 수와 대조한다.

## 8. 알려진 한계

- **템플릿은 여전히 base 의 구조를 낸다.** `--allow-unrepresented` 로 뽑은 템플릿을 채우면 항상 base 의 문단 구성이 나온다. `unrepresented` 를 안 읽으면 그것을 모른 채 쓰게 된다 — 그래서 기본을 거절로 뒀다(§3)
- **어느 문서의 값을 sample 로 쓸지 정할 수 없는 노드는 조용히 키에서 빠진다.** §5 규칙 1 이 그것인데, 그 노드는 `unrepresented` 에도 안 들어간다(매칭 자체는 됐으므로). 문서 3벌 이상에서만 생기는 경우다 — 2벌이면 매칭 여부가 곧 전부다
- **앵커 없는 `'r'` 구간의 잘못된 짝짓기가 여기서는 더 비싸다.** LCS 설계 §9 가 적은 한계 — 매칭 앵커가 없는 구간에서는 위치 짝짓기가 서로 다른 것을 짝지을 수 있다 — 가 `tmpl` 에서는 **잘못된 가변 키**를 만든다. `diff` 에서는 항목 하나가 틀린 것으로 끝나지만, 여기서는 그 키가 템플릿에 `{{k}}` 구멍으로 박히고 이후 생성되는 모든 문서에 퍼진다. 정확한 매칭은 유사도 비교가 필요해 범위 밖이며(같은 설계 §9), **`diff` 로 먼저 두 문서를 보면 `structure` 항목이 그 구간을 신고한다** — 그것이 지금 할 수 있는 최선의 방어다
- **런 분할** — LCS 설계 §9 와 같은 이유로 여전히 "같다" 로 보지 않는다

## 9. 범위 밖

- **선택적 블록**(`{{#if}}` 류) — `patch` 에 insert/delete 연산이 필요하다. 그 연산은 multipart 스펙 §12 가 미뤄둔 것이고 슬라이스 서너 개짜리다
- **파트 집합이 다른 문서** — §5 규칙 3
- **`Fill` 변경** — §6
- **`unrepresented` 비율로 자동 거절** — 임계값은 임의의 숫자다. `diff` 가 "차이 수를 세어 보고하고 게이트는 소비자가" 로 간 것과 같은 이유로, 여기서도 세어 싣기만 한다. 플래그가 이미 그 결정을 사람에게 넘겼다
