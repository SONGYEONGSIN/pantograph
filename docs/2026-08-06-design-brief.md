# BRIEF — 문서 제작 하네스 시스템 설계와 네이밍

## 목표

Word·Excel(스프레드시트)·PDF·웹PPT(PPTX)를 **에이전트가 완전히 제어**하는 하네스 시스템의 설계와 네이밍. 핵심 요구는 **높은 정확도의 문서 재현**이고, 이를 어떻게 구현할지에 대한 심도 있는 논증이 결과물의 중심이다. 여기에 **llm-wiki 기반 자동 루프 학습**을 붙여 시스템 자체가 진화하게 한다.

## 대상

이 하네스를 설계·구현할 사람(레포 소유자)과, 그 위에서 문서를 조작할 에이전트. 즉 결과물은 **구현으로 이어지는 기술 설계 문서**여야 하고, 마케팅 소개서가 아니다.

## 사용자 답변으로 확정된 것 2

| 질문 | 답 | 설계 함의 |
|---|---|---|
| "높은 정확도 재현"의 정의 | **시각 재현** — 시안·PDF를 보고 똑같이 만든다 | 렌더 → 픽셀 비교 → 보정 루프가 아키텍처의 중심. 왕복 무손실은 그 자체가 목표가 아니라 전제 |
| llm-wiki 루프의 진화 대상 | **둘 다** — 실패 사례를 쌓고, 그 실측으로 조작 레시피를 고친다 | 증거(실패) → 원칙(레시피) 사슬. repick-prompt의 DNA 루프와 같은 구조 |

## 참조 이미지에서 읽은 것 (기능 목록)

오픈소스·무료 / AI 기반 CLI + JSON / 설치 불필요 단일 바이너리 / 어떤 언어에서든 호출 / **경로 기반 요소 접근** / **원시 XML 대체** / 에이전트 친화 내장 렌더링 엔진 / **헤드리스 HTML·PNG 출력** / 형식 간 템플릿 병합(`{{key}}`) / **왕복 덤프 → 배치 JSON** / 실시간 미리보기 / 헤드리스·CI / 크로스 플랫폼 / 워드+엑셀+파워포인트

## 세운 가정 — 사용자 확인 필요

1. **기능 목록과 "시각 재현"은 층이 다르다.** 경로 접근·왕복 덤프·원시 XML 대체는 에이전트가 문서를 정밀 조작하는 **제어 수단**이고, 헤드리스 렌더링·픽셀 비교는 재현이 맞는지 판정하는 **합격 기준**이다. 대립이 아니라 수단/기준 관계로 놓았다.
2. **결과물은 설계 문서**다(아키텍처 + 네이밍 + 정확도 전략 + 진화 루프). PRD/사업계획서가 아니고, 구현 코드도 아니다.
3. **구현 언어는 열어둔다.** "단일 바이너리 + 어떤 언어에서든 호출"이 Go/Rust를 강하게 시사하지만, 선택 자체를 결과물이 **근거와 함께 논증**하게 한다 — 지금 못 박으면 그 논증을 잃는다.
4. **네이밍은 3~5개 후보 + 각각의 근거**로 받는다. 하나만 제시하면 고를 수가 없다.
5. 대상 문서는 OOXML(docx·xlsx·pptx) + PDF. 한글(HWP)·구글 문서는 이번 범위 밖으로 둔다.

## 보유 자료

- 참조 이미지의 기능 목록(위)
- 이 레포(repick-prompt)에 실제로 도는 llm-wiki 자동 루프 구현체 — 볼트(원본) → 생성물 → 드리프트 가드 FAIL, 라틴 방진 블라인드 심사, ledger 기반 반증, 백로그 큐. 진화 루프 설계의 **작동하는 선례**로 인용 가능
- 없는 것: 목표 정확도의 정량 기준, 벤치마크 문서 세트, 성능 예산 → 결과물이 `[확인 필요]`로 남기거나 스스로 기준을 제안해야 함
