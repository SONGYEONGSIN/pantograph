# Pantograph

문서를 **정확히 재현하는** 하네스. 에이전트에게 Word·Excel·PowerPoint·PDF에 대한 제어권을 주고, 재현이 맞았는지를 **기계가 판정**한다.

> 팬터그래프는 한 팔이 원본을 훑으면 다른 팔이 사본을 그리는 제도 기구다. 두 팔이 물리적으로 연결돼 있어 어긋날 수 없다.
> 이 시스템에서 그 연결부가 **렌더 → 비교 → 보정** 루프다.

- [설계 브리프](docs/2026-08-06-design-brief.md) — 전제와 확인이 필요한 가정

## 핵심 주장

**재현은 생성 문제가 아니라 측정 문제다.**

기존 방식(객체 모델 라이브러리 / LLM이 OOXML 직접 생성 / 상용 변환 API)은 저마다 다른 이유로 실패하지만 공통 결함이 하나 있다 — **틀렸는지 아는 방법이 없다.** 사람이 문서를 열어보기 전까지 재현 실패가 드러나지 않는다.

Pantograph는 차이를 **경로 단위로** 측정한다. 전체 페이지 픽셀 diff는 쓰지 않는다 — 1px 밀림이 페이지를 빨갛게 만들고, 무엇보다 어디를 고쳐야 하는지 알려주지 않는다.

## 역할 분담

| | 담당 |
|---|---|
| 시스템 | 차이를 **경로·속성·기대값·실제값**으로 가리키는 것까지 |
| 에이전트 | 그 경로에 대한 패치 생성 |

자동 보정 규칙을 시스템에 넣지 않는 이유는 그 규칙이 굳으면 **학습 루프의 대상이 사라지기** 때문이다.

## 다음 작업

1. **벤치마크 문서 세트 구축** — 합격 임계를 여기서 도출한다. 세트 없이는 진화 루프가 무엇을 향해 학습하는지가 없다
2. **docx 수직 슬라이스** — 덤프 → 패치 → 렌더 → 비교 → 루프를 한 포맷에서 끝까지. 포맷 확장은 그 뒤
3. `{{key}}` 형식 간 병합의 의미 정의 (설계에서 미해결로 남은 유일한 항목)

## 알려진 한계

- **렌더러는 실제 오피스 앱이 아니다.** 설계로 닫히지 않는 위험이라, 격차 자체를 기록해 추세를 본다
- **폰트가 정확도의 상한을 만든다.** 시안의 폰트는 픽셀에서 역추론할 수 없다
- **"단일 바이너리"와 "렌더 충실도"는 둘 다 가질 수 없다.** 내장 렌더(빠른 루프) + LibreOffice(정밀 판정) 2단으로 나눴다

## 계보

설계는 [repick-prompt](https://github.com/SONGYEONGSIN/repick-prompt)의 `/reprompt`로 깎았고, 진화 루프 구조도 그 레포가 실제로 돌리는 패턴(볼트 원본 → 생성물 → 드리프트 FAIL, 라틴 방진 블라인드 심사, ledger 기반 반증)을 문서 재현 도메인에 맞게 재해석한 것이다. **구조를 공유하되 인스턴스는 분리한다** — 두 볼트가 같은 이름 공간을 다투지 않도록.
